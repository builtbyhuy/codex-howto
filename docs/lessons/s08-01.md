## Understand the concept

A checkpoint is useful only when you know which state it captures. The Claude source describes automatic snapshots with a dedicated rewind interface. Do not transfer that promise to Codex. In Codex, a saved chat preserves conversation history, a Git commit preserves selected repository files, and a backup preserves whichever files were actually copied. These mechanisms overlap only partly and must be evaluated separately.

Before a change, identify three state boundaries: the chat, the working files and external systems. Starting or forking a chat can change the conversation context without reverting files. Restoring a file through Git does not erase the conversation that discussed it. An email, published release or database change cannot be undone merely by returning to an earlier chat message. Plan recovery around the actual resource being changed.

The official CLI guide recommends Git checkpoints before and after tasks. In a practice project, inspect the starting state, preserve unrelated work and use a small baseline commit or separate copy. Record the command needed to check behavior. This makes experimentation measurable: you can compare the baseline and candidate, rather than relying on a vague recollection that the project seemed to work before.


## Explore the details

### Name the protected content before experimenting

The supplied starter copy is a concrete baseline: you can open it and compare the candidate. An optional staged Git tree protects eight named starter paths for this exercise. Neither is an automatic Codex snapshot of the conversation, machine, ignored files or external services.

Use the recovery guide to make a deliberate heading experiment, then inspect the resulting file. A new chat changes context; it does not restore the heading. The useful later paragraph in the next exercise makes whole-file restoration an observable loss counterexample.


### Small experiments reduce recovery cost

A focused change to one document is a better first exercise than a broad refactor. Keep generated files, local configuration and external actions outside the initial experiment. If the task later needs a database migration or publication, design a separate recovery procedure for that system. A checkpoint label is not a guarantee of transactional rollback across every connected tool.



## Example

### Ask for a recovery plan before a local experiment

```text
Before changing this scratch project, inspect its current state and identify unrelated edits. Explain what protects the chat history, the files and any external state. Propose a small file baseline and a behavior check. Do not claim a chat fork restores files, and do not run a destructive reset or contact external services.
```

## Try the workflow

1. Choose one harmless local task and list the conversation, files and external resources it might affect.

2. Inspect existing changes, then make a baseline commit or separate copy only after identifying the intended files.

3. Record a small behavior check and its starting result before asking Codex to make the experimental change.

4. Inspect the candidate and decide whether to keep, refine or restore the affected files using the recorded baseline.

## Common mistakes

- Treating a saved chat as a complete filesystem snapshot with universal undo.

- Starting an experiment before checking whether another person already has uncommitted changes in the project.


## Troubleshooting

A supposedly safe restore loses unrelated work.

The baseline scope or later edits were not inventoried.

Compare named files and preserve unrelated content before recovery.

The baseline test result is described as a passing project.

Intentional exercise failures were hidden.

Record 4 pass and 2 fail explicitly; use the reference only as a comparison.

## Knowledge check

Forking a chat is sufficient to undo which of these automatically?

1. Every file written after the fork point.
2. A message already sent to an external service.
3. Neither; conversation branching alone establishes no file or external rollback.

<details><summary>Reference answer — attempt first</summary>

3. Neither; conversation branching alone establishes no file or external rollback.

A fork copies conversation history. File and external-state recovery require their own verified mechanisms.

</details>
