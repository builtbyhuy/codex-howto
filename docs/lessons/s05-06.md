## Understand the concept

The source lesson runs Claude itself as an MCP server. There is no supported command-name substitution for that example in current Codex. OpenAI's migration page states that codex mcp-server and the standalone codex-mcp-server binary have been removed. This affects hosting Codex behind MCP, not Codex's ability to connect to external MCP servers. Keep those directions separate: an agent consuming tools is different from another application invoking the agent.

OpenAI points integrations needing authentication, history, approvals and streamed events toward the Codex app server. It uses its own JSON-RPC protocol and is not an MCP server or a drop-in replacement for an MCP client. The migration guidance also marks the app-server command experimental and unsupported for production workloads. Those constraints matter more than a similarly shaped launch command. A real migration must review protocol messages, lifecycle handling, approvals, failure behavior and the support level before changing a live integration.

Choose the smallest interface for the outcome. Documentation uses external MCP. A bounded README summary can use codex exec and its checked process/output contract. A custom conversational client needs app-server’s thread/turn/event lifecycle, current schema and approval handling. Read app-server-migration.md and run its complete fixture/client pair, then compare the actual sequence with the MCP transcript. The fixture is a real subprocess but explicitly not Codex; native compatibility is a separate deliberate learner stage.

The supplied app-server-client.cjs sends initialize, the app-server-specific initialized notification, thread/start and turn/start, then waits for the returned turn’s turn/completed event and that same turn’s completed agent-message text. Unlike MCP, its wire omits the jsonrpc header. Its teaching path launches an explicit protocol fixture. Failed/interrupted turns, an empty completed result, malformed stdout, missing executable and early exit are checked failures. A completion event is only a candidate until stdout is drained and transport teardown is checked. Wrong-turn messages, malformed trailing stdout and a natural nonzero exit cannot produce success. The receipt distinguishes a natural process exit from deliberate post-result termination by the client. Command/file-change approvals are declined. app-server-migration.md also gives an explicit --native path, installed-version schema generation and read-only scratch setup. That stage can create conversation history and consume account usage; the offline checks do not perform it.

The author additionally checked installed codex-cli 0.163.0-alpha.11 without starting a thread or turn: app-server help and schema generation succeeded in a separate temporary configuration home, followed by a native initialize/initialized handshake. Its ThreadStartParams schema requires sandbox="read-only"; the returned SandboxPolicy uses type="readOnly". These are distinct shapes, and the client follows the installed schema rather than copying a conflicting illustrative spelling. The fixture and eight failure/lifecycle checks validate the teaching client; account-backed native generation remains unrun.

## Common mistakes

- Replacing claude mcp serve with codex mcp-server based on an old tutorial.

- Assuming that any JSON-RPC-speaking process is an interchangeable MCP server.


## Troubleshooting

A replacement process starts and is called a migrated integration.

The caller still speaks the old protocol.

Verify the entire request/response contract rather than process startup alone.

A healthy workbench server is used to claim Codex still serves MCP.

The two integration directions were conflated.

Trace who is client and who is server in each case; keep the removed-command finding intact.
