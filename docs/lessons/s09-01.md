## Understand the concept

Advanced features are useful when they solve a specific coordination problem. Planning helps resolve consequential choices before edits. Reasoning controls can give a difficult investigation more effort. Permission settings define execution boundaries and review. Non-interactive runs make a bounded workflow scriptable. Scheduling decides when a stable workflow starts. None of these alone defines what the user needs or proves the result works.

The source overview groups many Claude capabilities together. Codex offers related workflows, but commands, execution surfaces, and availability are different. This module follows the same seven source topics and teaches the Codex mechanism for each, with explicit differences. Keep app, CLI, IDE, and cloud-hosted work separate: a local path, browser sign-in, or running process is not automatically available in another environment.

Choose one outcome and map each feature to a real need. A two-file documentation correction may need only ordinary local editing and a link check. A broad refactor may need a plan, a versioned checkpoint, scoped changes, and multiple verification stages. Increasing effort or running more agents cannot compensate for unclear requirements. A good advanced workflow has visible evidence and a stopping condition, not just more automation.


## Explore the details

### A worked feature decision

The missing-checks review already has fixed input and a deterministic answer. Start by running the local tool and evidence validator; a scheduler or more reasoning adds little to that single task. The proposed missing-both extension introduces a design choice about accepted inputs, so a short plan is useful. A future repeated report might justify a headless command only after its output contract is stable. Each feature earns its place by solving a concrete problem.


### A complete advanced outcome

The extension task is implemented and graded through actual files and a real stdio server, with a readable reference change. The native tracks then teach the client controls needed to run the same work. Their account-dependent steps remain available to the learner even where the course author did not execute a model session or schedule.

- The final artifact passes schema and fixture-evidence validation.

- The workflow has a bounded deliverable and does not silently change permissions, accounts, schedules, or connections.

## Reference solution

Use the smallest pipeline that proves the result: discover the fixed fixture tools, inspect one fixture, and validate the findings.

1. State the deliverable: an evidence-backed review of missing-checks, with no edits, network, accounts, or arbitrary file access.

2. Run the local exchange. Trace initialize, notifications/initialized, tools/list, then tools/call; keep discovery separate from a successful review.

3. Match the missing-verification finding to the fixture's actual missing heading. A parsed object without evidence is not sufficient.

4. Validate the supplied reference result and record it as a deterministic fixture result, not a Codex-generated answer.

5. If you later ask Codex to perform this journey, record the real client and observed tool calls separately. Use planning or a reasoning comparison only when the task has enough uncertainty to justify it.

## Common mistakes

- Enabling every advanced feature before identifying the problem it should solve.

- Describing a plan, started process, or prepared schedule as a completed product.


## Troubleshooting

The workflow ends after tools are listed.

Discovery was mistaken for completion of the user request.

Call review_fixture_readme with a known fixture ID and check the returned evidence.

A report says the entire repository was reviewed.

The conclusion exceeds the fixed fictional inputs actually inspected.

Scope the report to the selected fixture and name the checker’s heading and injection-pattern limitations.

## Knowledge check

What should determine whether a task needs advanced features?

1. The number of features available in the menu.
2. The assumption that more effort always produces a better result.
3. A concrete uncertainty or execution requirement.

<details><summary>Reference answer — attempt first</summary>

3. A concrete uncertainty or execution requirement.

Select controls because they solve the task's actual problem. A simple change can be delivered reliably without a complicated workflow.
