## Understand the concept

Command hooks receive a JSON object on standard input. Shared fields identify the session, current directory, event, and optional transcript location; event-specific fields carry tool inputs, tool results, or stop state. Read only the fields your handler needs and validate their types. A transcript path is a convenience, not a stable parsing interface, and the transcript may contain sensitive material.

Output must match the event. For example, a PreToolUse denial uses hookSpecificOutput with hookEventName, permissionDecision, and its reason. A Stop continuation uses decision block and a reason instead. The same-looking word block therefore has different effects at different lifecycle points. Several fields are parsed but unsupported for particular events, so a syntactically valid JSON response can still be operationally wrong.

Keep diagnostic logs on standard error and machine-readable response data on standard output. In this lab, malformed input handled by the running guard deliberately becomes a supported denial response at exit zero; successful process exit means the response was emitted, not that the proposed patch was allowed. A missing executable or crash is different because it may produce no usable policy response. Oversized model-visible context can spill to a temporary file, so never return secrets on the assumption that truncation removes them. A compact, typed result is easier to inspect and maintain.


## Explore the details

### A useful failure is distinguishable

For the same input, distinguish policy denial from missing runtime, unreadable fixture, malformed JSON, and timeout. If all five produce the same vague message, an operator cannot know whether a safeguard worked. Record these outcomes explicitly in your test table. For prevention-sensitive workflows, also verify the documented runtime failure behavior; a crashing validator should never be assumed to have denied an operation.


### Evidence must describe the latest artifact

The Stop example links a SHA-256 hash to the actual candidate and independently inspects both required headings. A copied all-passed record cannot conceal a missing heading, and editing the candidate makes the old hash stale. This protects the narrow classroom contract; it does not evaluate arbitrary prose or guarantee that every claimed external test actually ran.

## Reference solution

The answer is an event-correct wire contract with explicit handling for invalid and irrelevant input.

1. Validate a matched event's absolute cwd and string tool_input.command before inspecting patch headers.

2. Keep diagnostics on stderr and one supported JSON response on stdout.

3. For deny or invalid input after launch, return PreToolUse permissionDecision deny; exit 0 means the response was emitted successfully.

4. For irrelevant tools, return no hook decision and document coverage rather than guessing their argument schema.

5. Keep process launch failure distinct: no running program means no policy response was produced.

6. For native practice, follow NATIVE-CLIENT.md through discovery, current-definition trust, covered tool observation and disabling; record unrun stages honestly.

## Common mistakes

- Printing debug messages before JSON on stdout and breaking the response contract.

- Returning a source product's accepted field and assuming Codex honors it identically.


## Troubleshooting

The process exits zero, so a learner assumes the patch was allowed.

Process success was confused with the denial decision inside stdout.

Inspect hookSpecificOutput.permissionDecision and the actual client result separately.

JSON parsing fails in the receiving client.

Logs were mixed into stdout or the event output shape is wrong.

Replay the fixture locally; keep stderr separate and compare against the documented PreToolUse fields.
