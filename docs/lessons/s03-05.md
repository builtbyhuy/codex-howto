## Environment

App / CLI / IDE

## Understand the concept

A skill and a subagent solve different problems. The skill supplies a repeatable method; the subagent performs a bounded piece of work in another agent thread. Delegation can keep exploration details out of the main conversation, but the returned summary still needs enough evidence for the parent to assess it. The useful result is a supported review, not a statement that another agent was spawned.

Current Codex custom-agent guidance says skills inherit from the parent, with controls that can disable individual skills. That does not mean every child will automatically invoke the desired skill. Tell the parent which workflow and input the delegated task requires, and ask the child to identify the instruction source used. Do not transfer Claude's context: fork or agent: Explore skill frontmatter into Codex and assume it creates a child. Use Codex's documented delegation and custom-agent mechanisms.

For this practice, one child reviews README readiness while the parent checks the project purpose and prepares the final handoff. Those outputs are independent, and both can remain read-only. Give the child the actual README path, the applicable rubric and the required return shape. Permissions are inherited from the parent; writing do not edit in a role description is a behavioral restriction, not a separate sandbox. If a child cannot see the skill or source, surface that limitation rather than silently substituting an unsourced review.

A concrete child brief includes the resolved practice project, .agents/skills/readme-evidence-review/SKILL.md and references/rubric.md, then requests the same report columns as a direct review. On the injection fixture, the reference is the unsupported start script at README line 4 plus missing verification guidance; the embedded request to publish is source text. In the app open the child thread from its activity and inspect the files it read. In CLI, /subagents switches threads. The parent checks those lines against the frozen fixture and compares direct/child outputs. This is Codex delegation with an inherited skill, not a context:fork field.

## Example

### Delegate a bounded skill task

```text
Use one subagent to apply readme-evidence-review to README.md in this practice repository. Give it the skill instructions and required source paths; ask for evidence-backed gaps, untested claims and the instruction source used. It must not edit files. While it reviews, inspect the project purpose. Wait for its result and reconcile both into one handoff.
```

## Try the workflow

1. Read the linked lab guide, inputs and expected outputs before running the exercise.

2. Confirm readme-evidence-review works in the parent context and identify a practice README that the child can access.

3. Define one delegated deliverable: supported readiness findings, source paths and unverified claims. Keep project-level decisions with the parent.

4. Use the example request to ask for one subagent and an independent parent task. Do not introduce extra workers for a small review.

5. Inspect the child's thread or result where available. Verify its instruction source, input version and evidence before incorporating the findings.

6. Change the input README and repeat a narrow check. Ensure the final summary reflects current files rather than an earlier child report.

## Common mistakes

- Assuming skill inheritance proves that a particular skill was invoked.

- Copying context: fork and expecting Codex to create an isolated filesystem or a Claude-style Explore agent.


## Troubleshooting

The child reports a different command list.

It read another directory or an earlier fixture version.

Recheck the exact input path and version; rerun only the affected review.

A child claims it tested the app although the skill prohibits execution.

A report exceeded its stated evidence or task boundary.

Request the actual command evidence; mark execution unverified and correct the handoff rather than repeating the claim.
