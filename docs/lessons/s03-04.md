## Your outcome

Separate explicit selection, implicit matching and action permission when designing skill activation.

## Environment

App / CLI / IDE

## Understand the concept

Explicit invocation names the workflow you want; implicit invocation lets Codex select a matching description. Use explicit selection while learning or diagnosing a skill so you know which procedure was intended. Then test normal phrasing to evaluate discovery. Client affordances differ: the documented CLI and IDE options include /skills and dollar-name mentions. Use the selector actually available in the app rather than assuming Claude's slash-command syntax is portable.

Codex supports an optional agents/openai.yaml file for skill metadata and policy. Setting policy.allow_implicit_invocation to false prevents automatic selection while leaving explicit invocation available. This is different from a permission boundary. A user-invoked release-draft skill still needs an explicit task to publish, send or change a live system; choosing it does not authorize every action its text mentions. Conversely, disabling implicit invocation does not make a procedure harmless once someone selects it.

Build a two-column activation test rather than relying on one successful call. Put requests that name readme-evidence-review in the first column and ordinary readiness questions in the second. Add a nearby but wrong task such as rewriting an advertisement. Record what was selected and what was produced. If you add the explicit-only policy for a sensitive workflow, rerun both columns. Do not copy Claude's disable-model-invocation or user-invocable frontmatter and claim they have the same meaning in Codex.

Use --explicit-only to prepare a second fresh project. It places the policy at the actual agents/openai.yaml path inside the copied skill and creates activation-results.csv with unrun observations. In the first project test a direct selection, a plain readiness question and unrelated styling; repeat those exact requests in the explicit-only project. Require the same two grounded findings whenever the skill is actually invoked. This fixes input and procedure while changing only discovery policy. If a native result selects correctly but invents a third defect, score selection as correct and the report as incorrect.


## Explore the details

### Practice and acceptance

An explicit-only policy changes discovery behavior; it cannot make an incorrect report correct or authorize side effects.



## Example

### A complete optional Codex invocation-policy file

```yaml
# .agents/skills/readme-evidence-review/agents/openai.yaml
interface:
  display_name: "README Evidence Review"
  short_description: "Inspect documented run and test claims"
policy:
  allow_implicit_invocation: false
```

## Reference solution

Direct and implicit invocation need their own observations; allow_implicit_invocation:false leaves explicit invocation available.

1. Use the complete skill's narrow description as the baseline and keep fixtures unchanged.

2. Run helper checks to establish output behavior without claiming host selection.

3. For optional Codex cases, record the exact request and visible selection/source evidence before grading the result.

4. Apply an explicit-only draft only in the chosen scratch package, refresh as required and compare the same requests; keep authorization boundaries unchanged.

## Worked reference

### A two-axis result sheet

One case can select correctly and still produce a false finding.

```text
Case: complete README review
Expected activation: yes
Expected findings: none
Case: redesign colors
Expected activation: no
```

```text
Helper output on complete: findings=[]
Client activation: record actual observation, not supplied by this helper
```

## Common mistakes

- Using a Claude invocation-control field in Codex without checking support.

- Assuming an explicitly selected skill may perform every side effect described in its examples.


## Troubleshooting

The policy is called ineffective because a direct mention still works.

Explicit invocation was confused with implicit matching.

Test a paraphrase without direct selection; explicit selection is documented to remain available.

An unrelated request returns a plausible answer and is counted as skill activation.

Fluent output was used as invocation evidence.

Inspect the actual client selection or instruction-read evidence, and mark activation unknown when unavailable.

What does allow_implicit_invocation: false establish?

1. The skill cannot make file changes under any circumstances.
2. The skill is hidden from every user and client.
3. Codex will not choose the skill implicitly; explicit selection still works.

It controls implicit selection, not the permissions or correctness of an explicitly invoked workflow.
