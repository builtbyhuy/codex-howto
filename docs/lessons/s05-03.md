## Environment

App / CLI / IDE

## Understand the concept

The word scope can describe several different things. Configuration scope answers where a server definition is stored and who may inherit it. OAuth scope describes permissions requested from an authorization server. Tool visibility describes which operations the client exposes. The user's task scope describes the work being delegated. Do not collapse these into a single permission decision: a project-shared server definition can exist while a teammate lacks service access, and a valid token can permit more than today's task authorizes.

Codex documents user configuration in ~/.codex/config.toml and project configuration in .codex/config.toml for trusted projects. That differs from the source guide's Claude local, project and user files and --scope syntax. A project entry is useful for reproducible non-secret connection details, but reviewing repository trust and managed requirements still matters. Sharing a URL is not sharing the right to retrieve all private content, and sharing an environment-variable name must not turn into committing its value.

For the lab, prepare a project-scoped description of the public Docs MCP without applying it. Then compare it with a fictional private ticket connector. Identify what can be checked into a repository, what stays with each user's credentials, and which operations should be exposed. Codex's enabled_tools and disabled_tools settings can narrow the presented set, with the deny list applied after the allow list. Those controls should match actual tool names; they do not replace the service's authorization or validate a tool's safety.

Generate the complete host-specific table, then in a chosen scratch configuration keep all three names in enabled_tools and put get_task in disabled_tools. After restarting the native client, inspect whether get_task is absent while list_tasks and read_task_snapshot remain. The standalone transcript still lists all three because it never reads Codex TOML. A hidden lookup also does not hide those records from read_task_snapshot. Project configuration, tool presentation and data authorization therefore have different tests. App/CLI/IDE on the same host share this connection; another machine cannot reuse the first machine’s executable path just by copying its file.

## Worked reference

### An unknown operation is not a hidden write permission

The protocol test calls a name absent from the catalogue.

```text
{"method":"tools/call","params":{"name":"erase_all","arguments":{}}}
```

```text
error.code: -32602
error.message: Unknown tool: erase_all
```

This is server-side name validation. It is independent of whether a future host allows a known tool.

## Common mistakes

- Copying Claude's --scope project or .mcp.json into a Codex setup without checking the format.

- Assuming that adding a project connection grants every teammate the same data access.


## Troubleshooting

A read-only annotation is treated as access enforcement.

Annotations describe tools; the implementation and host permissions enforce behavior.

Inspect the actual tool branches and restrictions instead of relying only on readOnlyHint.

The draft allow-list is said to have filtered the harness.

The harness never loads Codex configuration.

Label TOML inactive and test host enforcement only in an actual deliberately configured client.

A teammate has your project MCP entry but cannot read a private ticket. What is a likely distinction?

<details><summary>Reference answer — attempt first</summary>

3. Configuration sharing does not supply the teammate's service authorization.

A connection definition and an authenticated identity are separate; each user needs appropriate service access.
