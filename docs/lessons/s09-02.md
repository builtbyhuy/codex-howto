## Understand the concept

Plan mode gives Codex room to inspect context, ask about material ambiguities, and propose an approach before editing. In the app, /plan is a documented entry point; supported clients also expose planning controls. Use it when several implementation choices affect behavior, data, or maintenance. A clear single-file correction usually does not benefit from an elaborate planning phase.

A useful plan describes the starting state, intended behavior, constraints, affected areas, verification, and unresolved decisions. It should explain why the chosen approach fits, rather than merely listing generic development steps. Distinguish observation from assumption: a repository convention found in a file is evidence, while an inferred user preference should be labeled. The plan must preserve existing work and avoid broad unrelated changes.

In the app use /plan, with Shift+Tab available in supported clients; CLI users can also enter /plan. If the native control is absent, a written read-only request can still organize thinking but is not evidence of an enforced mode. Leave Plan mode deliberately before implementation, then run the checks against actual changed files. This lesson finishes with the extension artifact rather than stopping at an approval checklist.

## Common mistakes

- Using planning as an endless substitute for producing the delegated result.

- Treating a plan-mode label as an enforced security boundary or authorization for live-system changes.


## Troubleshooting

The direct checker accepts the new fixture but MCP rejects it.

The server’s advertised input contract and implementation have drifted.

Use the shared IDS list for discovery and validation, and test a real tools/call for the new ID.

The new case passes after arbitrary paths were added.

The implementation changed the trust boundary beyond the plan.

Return to the fixed-ID design; add a negative path-traversal case and review the diff.
