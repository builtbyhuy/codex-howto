## Your outcome

Select a repeatable local task whose inputs, permissions and verification make scripted execution useful.

## Environment

App-based lab / Optional CLI

## Understand the concept

The strongest first CLI use case is a task with clear local inputs and an easy result check. Examples include summarizing documented setup, drafting release notes from a selected diff, identifying unsupported README claims or explaining a failing test log. These tasks reduce repetitive reading without requiring the agent to publish, change accounts or coordinate a complex external workflow. Start with a real recurring need, not with a desire to automate everything.

Choose an input boundary and output contract before running the agent. A release-note draft should name the exact diff or commit range. A log explanation should separate observed error messages from hypotheses. A small code fix should identify the failing behavior and the relevant test. A large prompt that simply says “improve the repository” lacks a stable basis for either safe execution or meaningful acceptance.

Repeatability requires more than a command that runs twice. Record the source version, working directory, client assumptions and validation method. If a report changes, you should be able to tell whether the source changed or the task was underspecified. For edits, preserve a baseline and inspect the final diff. For read-only analysis, compare the answer with the named inputs. Keep publication, scheduling and external communication as separate authorized actions.


## Explore the details

### A useful pipeline has an input and an acceptance rule

The batch has two explicit inputs, two distinct project names and two documented commands. verify-extraction.cjs accepts each current answer against its own source and rejects a crossed directory, fabricated claims, malformed JSON, missing fields and undocumented source. These results establish the offline consumer contract, not AI generation quality.

The provided synthetic log shows uppercase and padded-query failures. A grounded draft cites expected=2 actual=0 and proposes normalization as a hypothesis tied to notes.cjs; it does not announce a deployment outage or claim a fix ran. Use the app while exploring the task, then a one-shot pipeline after its inputs and check are stable.


### When to stay interactive

Stay interactive when exploring requirements or reviewing a visual result. Scripted execution fits a stable contract. Once the task works, package its repeatable guidance as a focused skill or reviewed script, keeping the uncertainty and verification requirements visible.

## Worked reference

### Prove a repeatable local reporting contract

Evaluate the supplied fixtures before connecting any real agent process. This is an offline workflow test.

```text
Input cases: completed / failed / malformed / incomplete / producer failure
Output contract: Markdown report + meaningful process exit
Acceptance: correct classification and preserved failure evidence
```

```text
Only the completed fixture returns exit 0.
Every failure class remains visible to a downstream caller.
No report is automatically published or treated as accepted business output.
```

A useful repeatable task needs a consumer that behaves correctly on missing and failed inputs, not merely a pleasant success summary.

</details>

## Common mistakes

- Automating a broad vague task before proving a small manual workflow works.

- Treating a polished draft as evidence that it was reviewed, sent or accepted by its intended audience.


## Troubleshooting

A clean or missing input produces invented release notes.

The prompt or consumer lacks an explicit empty-input outcome.

Require an honest no-relevant-changes result and test it before reuse.

The workflow is scheduled before its contract is stable.

A single successful run was mistaken for dependable repeatability.

First pass the local failure matrix and review the output; scheduling requires a separate decision.
