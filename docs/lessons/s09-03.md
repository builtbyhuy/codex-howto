## Your outcome

Choose a supported reasoning setting based on task difficulty and measured results.

## Environment

Codex app · CLI · IDE, as noted

## Understand the concept

Reasoning effort gives the selected Codex model more or less computation for a task. Begin with the current client default; a harder investigation may benefit from a higher supported setting, but extra time or output length is not success. This differs from Claude’s thinking keywords, environment variables and /effort interface.

In the app use the model/reasoning control beneath the composer; builds with a Power selector expose exact choices through Advanced. In the CLI use /model to choose a model and supported effort; the IDE uses its model switcher below the composer. A one-run CLI override is model_reasoning_effort. Available labels and values depend on the model, account and build, so choose two values actually offered for the same model.

Use two fresh copies of the missing-both task and identical prompts, tools, permissions and rubric. Change only the supported effort. Retain actual outputs, diffs, elapsed time and available usage; grade both with the same extension checker and baseline suite. The supplied synthetic candidate comparison tests the rubric only. One observed pair is task-specific evidence, not a universal model ranking.


## Explore the details

### Keep the comparison proportionate

One successful trial can suggest a direction, but does not prove a universal advantage. If the task matters, repeat on representative cases and include failures rather than selecting only the best result. Avoid rerunning a large expensive workflow solely to fill a table. It is acceptable to conclude that a comparison is not worth its cost for a small edit, or that current evidence is insufficient to recommend a change.



## Example

### Exact native controls · separate real sessions

```text
/model

# One-run CLI override, keeping the configured model:
codex --config model_reasoning_effort='"medium"'
# Compare only if the same model supports this value too:
codex --config model_reasoning_effort='"high"'
```

## Try the workflow

1. Use the app model control or CLI /model; record the actual model, default effort and two supported comparison choices.

2. Create two fresh generated packages, fix the extension prompt and acceptance checks, and keep tools/permissions equal.

3. Run the same bounded implementation in two fresh chats with one effort difference. Save actual outputs and diffs separately.

4. Run extension/check.cjs and the copied baseline suite for each. Record failures, elapsed time and available usage rather than selecting only a convincing answer.

5. Restore the original app selection. If a run is unavailable, label the comparison unmeasured; never borrow the fixture result as a model score.


## Your practice task

Carry out the two-session comparison when you have a supported authenticated client and want to spend its normal usage. The deliverable is the two actual artifacts, identical grading, selected native settings and a modest task-specific conclusion. The offline rubric rehearsal can be completed independently, but it is not the effort experiment.

## Common mistakes

- Requesting hidden chain-of-thought as though it were required evidence.

- Changing model, prompt, repository, and effort together, then attributing improvement to one control.


## Troubleshooting

Both candidates pass because they parse as JSON.

Only shape was validated, so a factual omission escaped.

Validate the complete result against the deterministic fixture evidence as well as the JSON schema.

A higher setting is declared better after only one run.

The baseline and changed input were not controlled.

Label the comparison unmeasured, fix the inputs, and run the same task in two supported settings if you choose to continue.
