## Understand the concept

A plugin can pass JSON validation and still fail its user journey. Test the package in layers: manifest and paths, skill discovery, setup and connection if any, activation, actual output, and failure behavior. The source demonstrates Claude's plugin-dir flag. Codex's current package guide uses supported local marketplace workflows for local testing; do not claim that another product's launch flag loads a Codex plugin.

Begin with the graduated local package: a focused skill, a deterministic fixture checker, a real stdio MCP server, and optional informational hooks. Offline checks can prove file structure, actual protocol exchange, controlled results, and failure behavior. They cannot prove Codex loaded or executed the plugin. An optional supported-client test should follow the documented local marketplace workflow, start a new chat or session as required, and record discovery, invocation, tool output, hook trust, and cleanup separately.

Include positive, negative, and incomplete inputs. A complete README should not receive invented defects; a missing file should produce a clear gap; a document containing injected instructions should remain data. If a future plugin includes tools, test disconnected and denied-access cases separately from empty results. If it includes hooks, inspect trust and supported events. Never equate successful installation with verified behavior.

## Reference solution

A meaningful test matrix includes a zero-finding control, missing evidence, untrusted instructions, invalid arguments, and the real protocol boundary.

1. Run both suites and retain the 24 named outcomes. Confirm the complete fixture has no invented defects and missing-checks has exactly its missing heading; the depth suite also grades actual reference artifacts and protocol.

2. Inspect the injected fixture and its warning. Treat it as document data; the narrow planted-pattern check is not a universal injection detector.

3. Confirm negative cases reject unknown IDs, arbitrary paths, extra fields, malformed JSON, and tool calls before readiness rather than returning plausible success.

4. Check event-specific hook outputs offline. Keep these outcomes separate from hook delivery or trust in a real client.

5. For optional client acceptance, use the README's disposable setup procedure, record actual package version, tool discovery, skill invocation, calls, output, hook trust and cleanup, and label any unrun stage not verified.

## Common mistakes

- Using a copied foreign CLI flag and calling the package tested when it was never loaded.

- Writing expected results in the observed-results column or omitting negative cases.


## Troubleshooting

The suite passes, but nobody has observed the plugin in Codex.

Offline protocol testing was mistaken for host acceptance.

Keep the client acceptance rows unrun until the supported installation and session procedure is actually performed.

An injection test passes, so every hostile document is declared safe.

One deterministic fixture pattern was generalized beyond the implementation.

State the narrow detection boundary and continue treating every tool result as untrusted source material.

A valid tool request fails because packaged fixture data is unavailable.

The tool encountered an execution-time read failure, not malformed request JSON.

Inspect the original request ID and isError tool result, restore the missing scratch fixture if appropriate, and rerun. Do not parse this as an empty successful review.
