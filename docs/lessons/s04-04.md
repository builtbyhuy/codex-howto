## Understand the concept

A chain is appropriate when a stage needs evidence produced by an earlier stage. Investigation establishes the actual failure and interface before implementation begins. Integration then waits for both implementation outputs. This does not require serializing every activity: once CONTRACT.md freezes normalized status inputs and report outputs, A and B can work independently. The dependency is between evidence and implementation, then between both implementations and integration.

The capstone makes those dependencies observable. The original starter produces done=1 and doneMinutes=80. A correct normalizer alone should repair the completed count but leave the all-task effort bug in B. The final target remains done=2 and doneMinutes=55. Use this partial candidate deliberately to test whether the integrator rejects an incomplete handoff. A statement that package A is done cannot satisfy package B's requirements.

A handoff should carry the input version, changed file, supported conclusion, observed checks and unresolved limits. The parent follows source references, inspects both diffs and runs the combined candidate. candidate.test.cjs adds independent invalid-input and aggregation cases, so a hardcoded fixture total is not an adequate solution. If a later edit invalidates earlier evidence, rerun the affected check against the new state instead of forwarding the earlier pass claim.

The worktree demo actually executes the partial-handoff experiment. In a temporary repository it copies only A’s repair into a separate checkout: the composed result becomes done=2,doneMinutes=80. After B’s repair it becomes 2,55. The temporary parent stays 1,80 until a reviewed two-file patch is applied and its own candidate grader passes. This is a falsifiable evidence dependency, not only an authored expectation. The program spawns zero agents; compare these observed code states with any actual investigator/worker handoffs you choose to run.

## Example

### Investigation, independent implementations, integrated verification

```text
Read labs/delegation-capstone/CONTRACT.md and reproduce the starter result. Return an investigator handoff identifying the missing trim and completed-only aggregation defects. Then implement A and B with disjoint file ownership. Require each handoff to name its actual checks. After both changes exist, inspect their combined diff and run node labs/delegation-capstone/run.cjs starter and node --test labs/delegation-capstone/candidate.test.cjs. Reject a candidate with only A fixed; record its remaining aggregation failure rather than calling the chain complete.
```

## Try the workflow

1. Run the baseline and write a factual investigator handoff naming the two defects and constraints.

2. Complete A and B against their independent frozen input contracts; do not serialize them merely because integration is a later stage.

3. Require each implementation handoff to name changed files, actual cases and unresolved limits.

4. Have the integrator wait for both packages, inspect their combined diff and run the real candidate.

5. Inject an incomplete handoff by leaving B unchanged; confirm the integrated check rejects the partial result.

## Reference solution

The useful chain is evidence -&gt; independent implementation packages -&gt; integrated verification. Its handoffs carry source and result evidence rather than status alone.

1. Record the baseline contract and failed result.

2. Implement both modules or inspect the supplied reference solution after attempting the task.

4. Accept only a combined candidate that meets normal, invalid-input and preservation requirements.

## Common mistakes

- Running investigation, implementation and final verification concurrently as if they had independent inputs.

- Treating a worker's reported pass as evidence that a later edited version still passes.


## Troubleshooting

The integrator starts while B is incomplete.

A completion dependency was omitted or ignored.

Wait for both file changes and handoffs; a partial integrated run is diagnostic, not accepted delivery.

An investigator says 'normalization bug' without source details.

The next worker must rediscover the evidence.

Include the function, input example, expected value and relevant line in the handoff.

## Knowledge check

When should final verification run?

1. At the same time as the worker, against whatever files happen to exist.
2. After the intended changes are integrated into the files being verified.
3. Only when every agent reports confidence.

2. After the intended changes are integrated into the files being verified.

Verification must observe the actual final state. Earlier checks cannot establish the correctness of later changes.
