## Understand the concept

The source chapter compares command, HTTP, prompt, MCP-tool, and agent hooks. Current Codex release documentation supports command and mcp_tool handlers; prompt and agent handlers are parsed but skipped. A configuration parser accepting a field therefore does not prove a feature executes. Treat direct HTTP and other source-specific types as unverified until the current Codex release documentation establishes a supported implementation.

A command handler runs a local program and communicates through the documented input and output channels. It is a good fit for deterministic checks you own, such as recognizing a forbidden fixture value or adding a compact context message. An MCP-tool handler invokes a tool on an already-connected server. It does not start or reconnect the server, request another tool approval, or recursively trigger additional hooks.

Synchronous and background execution solve different needs. Background command hooks can deliver informational output at a later safe point, but cannot block, approve, rewrite, or control the triggering operation. A late log is useful observability, not a preventive gate. MCP handlers run synchronously, but missing servers, errors, and unavailable tools do not automatically block the operation. Design failure behavior explicitly.


## Explore the details

### Compare actual handlers at the right boundary

The command guard returns a documented PreToolUse decision. The workflow-plugin MCP demo exchanges real local protocol messages and returns ordinary fixture findings. That proves a connection and a tool result, not an MCP hook decision. A real mcp_tool hook would additionally require an already-connected server, appropriate templated input, and event-correct output. Background information cannot replace a synchronous gate, and a missing callback is not an automatic supported denial.


### MCP input is a contract, not a server launcher

A documented mcp_tool entry identifies type, server, tool and input. A complete ${tool_input.command} value retains its JSON type; interpolation inside a larger string becomes text. Use the actual connected server/tool names from discovery. This lab’s fixture MCP result is ordinary review data, so it is not advertised as a ready-made blocking hook. Adding a hook definition neither starts that server nor turns its errors into a preventive gate.

## Reference solution

Select the handler from its actual control requirement and dependency, not from the source product's feature list.

1. Use the command handler when a deterministic check must inspect the supported PreToolUse payload.

2. Use the local fixture tool to obtain bounded structured evidence; inspect its fixed ID allowlist and read-only implementation.

3. Explain that the demo proves stdio tool connectivity, not an already-connected server inside a live Codex hook.

4. Keep native prompt/agent handlers labeled skipped in current Codex documentation, and keep async output advisory.

5. Test a missing server or handler as failure; do not infer that a callback error prevented the operation.

6. For native practice, follow NATIVE-CLIENT.md through discovery, current-definition trust, covered tool observation and disabling; record unrun stages honestly.

## Common mistakes

- Using async output as a guarantee that the triggering operation was prevented.

- Copying a source prompt or agent handler and assuming a silent skip means the review passed.


## Troubleshooting

MCP output appears where a hook decision was expected.

Tool-result JSON was copied directly into an event-specific hook response.

Add an explicit adapter using the supported event contract and test its runtime effect separately.

An async validator reports the problem after the write.

Background handlers deliver later feedback and cannot control the triggering action.

Use an appropriate supported synchronous path for prevention and verify its documented failure behavior.
