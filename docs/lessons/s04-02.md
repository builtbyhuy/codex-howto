## Understand the concept

A custom Codex agent is a named configuration for a recognizable responsibility. In this capstone, practice_normalizer owns package A: implementing normalizeStatus in starter/normalize.cjs against CONTRACT.md. Keep the stable role instructions separate from the current task input. The role can describe how to preserve unrelated work and report evidence; today's brief still needs the actual workspace, owned path, contract version and expected return.

Current Codex custom agents use standalone TOML files under a documented project or user agents directory. Required fields are name, description and developer_instructions. The lab supplies role-draft.toml outside active discovery paths so you can inspect it without installing anything. A later deliberate scratch-client test must verify that Codex actually loaded and used the role; a file that parses and a plausible normalizer report are not sufficient proof.

Subagents inherit the parent's execution settings, provider and MCP servers. A sentence saying own one file is a behavioral instruction, not an independent filesystem sandbox. Do not insert unsupported permission overrides into the role and assume they changed access. First verify the bounded code result with padded statuses, wrong types and unsupported values. Then, if a real custom-role exercise is performed, inspect both its actual role activity and its final diff as separate evidence.

For deliberate project activation, place the whole role draft at .codex/agents/practice_normalizer.toml inside the disposable lab. Current standalone files need no role registration table in parent config. The guide provides PowerShell and POSIX copy steps that preserve existing work. Start a fresh client context if needed, request practice_normalizer for A, then inspect its actual role activity and output. Omitted model/effort settings inherit parent defaults. Supported reductions such as features.shell_tool=false can remove shell execution for a read-heavy role, but are inappropriate for a worker expected to run checks. This file cannot override parent sandbox, approval, provider or MCP settings.

## Reference solution

The required three TOML fields define a bounded normalizer role. The role inherits parent permissions and cannot enforce its file ownership through prose alone.

1. Keep the role name distinct from built-ins to avoid accidental shadowing.

2. Supply CONTRACT.md, package A and starter/normalize.cjs as explicit task context.

3. Verify padded strings, non-string rejection and unsupported status behavior against the reference tests.

4. For a real client run, inspect the role actually used and the diff; do not infer loading from the presence of a TOML file.

## Common mistakes

- Copying .claude/agents/example.md and expecting it to become a Codex custom agent.

- Claiming a do-not-edit sentence creates a separate read-only sandbox.


## Troubleshooting

The agent edits another file despite the role description.

Behavioral instructions were mistaken for a filesystem sandbox.

Correct scope, inspect the diff and use the parent's actual permission controls as appropriate.

The role is never available in the client.

The draft is inactive or discovery/path/refresh differs from the intended environment.

Check the documented .codex/agents location and actual client evidence; do not change global permissions to compensate.

What happens if a custom Codex role claims its own mcp_servers configuration?

1. It automatically creates an isolated connector account.
