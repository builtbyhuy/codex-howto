Understand the approach

Codex discovers hook definitions alongside active configuration layers. Common locations include ~/.codex/hooks.json, ~/.codex/config.toml, and their project-level .codex equivalents. A definition has an event, an optional matcher group, and one or more handlers. A hooks.json file and inline TOML in the same layer are both loaded, with a warning; choose one representation per layer to avoid accidental duplication.

Layering matters because hook definitions are additive. A higher-precedence configuration does not simply replace all lower-level hooks. Project-local hooks require a trusted project configuration layer, and non-managed hook definitions still need their own review and trust. A user-level hook can remain active even when a project hook is unavailable. Inventory sources before diagnosing an unexpected double run.

Commands execute with the session's current working directory. A relative path that works at the repository root can fail when a session starts in a subdirectory. Prefer a reviewed absolute script path or the documented repository-root resolution appropriate to the host shell. Windows can use commandWindows in JSON; inline TOML accepts command_windows or commandWindows. Choose an interpreter that actually exists on the learner's host.

Generated is different from active

The hook-policy generator prints a real PreToolUse command draft using the current Node executable and handler path. Run its 13 checks first, then compare baseline and --solution targets. Follow labs/hook-policy/README.md if you elect a supported-client test in your own disposable Git repository. Review project trust and exact-definition trust separately, then observe one allowed and one denied scratch patch. Disable at the right scope

The documented features.hooks = false setting turns hooks off broadly; it is unnecessary for this exercise. Prefer the non-managed definition control or the generated project file. Managed definitions may be enforced and cannot be treated as ordinary learner-owned settings.

  5. Disable only the practice definition or rename only the generated project file, then start a fresh chat and inspect the loaded sources again.

From input to result

Supported draft structure

A local generator creates the event/matcher/handler structure documented for Codex.

Worked input javascript
const draft = {
  hooks: { PreToolUse: [{
    matcher: '^apply_patch$',
    hooks: [{ type: 'command', command, commandWindows, timeout: 10 }]
  }] }
};
Expected result · compare with your run
PreToolUse → ^apply_patch$ → command handler; timeout 10 seconds.

command and commandWindows are the actual paths printed by create-config-draft.cjs. This excerpt omits machine-specific paths; it is not evidence of activation.

When it does not work

The generated command no longer exists.

Likely cause: The lab was moved or a different runtime is being used.

What to try: Regenerate the draft from the new copy; do not blindly edit personal settings.

One operation produces duplicate feedback.

Likely cause: The same definition is active in more than one source or representation.

What to try: Inventory hooks.json, inline hooks, and plugin sources; remove duplication only within your authorized scratch scope.

Common mistakes

  • Copying ~/.claude/settings.json as though it were Codex configuration.
  • Defining the same handler in hooks.json and config.toml and expecting one to override the other.
Source mapping & differences · different

Codex uses hooks.json or inline hooks beside active Codex config layers, with additive loading and definition trust, rather than Claude settings-file placement.
