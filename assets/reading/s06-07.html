Understand the approach

A hook that produces no visible result may never have been discovered, may need trust review, may not match, may fail to launch, or may return output that the event ignores. Debug these stages separately. Repeatedly changing all configuration at once destroys the evidence. Start with the current source inventory and one fictional input that has a clear expected result.

In Codex CLI, /hooks exposes configured sources, review status, and controls for non-managed hooks. This is different from the source course's Claude debug flag and shortcut. Managed hooks can be enforced by policy and may not be disableable from the user browser. Reading their status does not authorize changing organization controls. Record the exact client and execution host before deciding a hook is absent.

Run a proposed handler independently with fictional stdin before connecting it. Check the interpreter, path quoting, cwd assumptions, stdout, stderr, exit status, and timeout. Then inspect event selection and trust separately. Concurrent handlers and background delivery can make observed order misleading; tag local test output with a fictional case identifier rather than inferring a sequential lifecycle from timestamps alone.

Retain a minimal incident record

Keep the client version, redacted configuration excerpt, fixture identifier, expected result, observed result, and one next experiment. Avoid copying a whole transcript when a single event explains the defect. The transcript format is not a stable hook interface and can include sensitive material. A compact incident record makes it easier to reproduce a bug after a runtime update and to tell a new configuration defect from a changed product contract.

About your environment

Verified October 21, 2026. /hooks is documented for Codex CLI. App surfaces and managed policy differ; use the actual available inspection tools and keep this lab inactive.

Try it step by step

  1. Run the unchanged policy suite and combined depth suite to isolate a code regression before touching client configuration.
  2. Replay one exact failing input and inspect stdout, stderr and exit status; distinguish an intentional deny from a launch failure.
  3. Inspect the generated absolute interpreter path and cwd assumptions on the actual execution host.
  4. In /hooks inspect source, enabled state, current trust and event/matcher. Change only the failing stage, then repeat the same covered operation.
  5. Restore any deliberately broken scratch copy, disable the practice definition and retain a concise before/after report with version and observed event.

Answer 3: The handler failed to launch; blocking behavior still needs separate verification.

Launch failure and policy success are different outcomes. Fix the path and verify the event's documented failure behavior.

When it does not work

The handler file exists but the command cannot launch it.

Likely cause: Runtime resolution or shell quoting differs from the draft.

What to try: Regenerate with the actual runtime and inspect commandWindows; replay locally before changing trust or permissions.

A changed hook was skipped after editing.

Likely cause: Definition trust is tied to the reviewed definition.

What to try: Review the exact changed scratch definition through supported controls; never bypass owner or managed policy.

Common mistakes

  • Using another product's debug switches and interpreting their absence as missing hook support.
  • Fixing a launch error by turning off trust review or assuming all handler failures block the tool.
