Understand the approach

Git records versions of selected files. A commit is useful because it identifies content you can inspect later, independently of a chat interface. It does not automatically include every file in the folder, preserve ignored outputs or snapshot an external service. Before calling a commit a recovery point, verify which files it contains and whether the working tree already had changes that must be preserved.

The default Orbit Notes --git setup stages the named starter files and records an index tree without creating a commit. It is a useful comparison baseline, but not durable history. The separate verify-commit demonstration creates a fresh owned repository and two actual commits using fictional author identity only for those invocations; it does not save identity settings or use a remote. In your own real repository, use its normal reviewed Git workflow and author identity instead of copying this fictional practice identity. Neither exercise requires changing global Git configuration.

After the Codex task, compare the working tree with the baseline and run the relevant project check. The chat explains the intent; the diff shows file changes; the check supplies behavior evidence. A later commit can preserve the accepted candidate, but committing is not the same as customer acceptance or deployment. Keep those milestones separate so a clean repository does not become a misleading claim that all work is finished.

Create and inspect a real practice commit

The separate verifier creates two actual commits only inside its newly owned temporary repository. Fictional author identity and disabled signing are invocation-only Git options; no identity settings are saved. The first commit deliberately records the broken starter, and the second records only the focused README and search fix.

Inspect the returned path, commit IDs, git ls-tree --name-only HEAD and git show HEAD:README.md. The draft stays untracked. A later README paragraph stays unstaged and is absent from HEAD. This makes history concrete while retaining the index-only default for earlier recovery exercises.

Verify coverage before naming a checkpoint

The optional setup stages .gitignore, AGENTS.md, README.md, WORK-NOTE.md, checks.cjs, cli.cjs, notes.cjs and notes.json. Inspect the actual staged list and tree identifier. Later git add changes the index; the exercise calls it a disposable comparison baseline, not durable commit history.

After the candidate, inspect the working diff and untracked draft separately. The offline demonstration restores one file from the index and confirms the draft survives. A real reviewed commit records selected content in history, but it still does not include untracked/ignored material or prove deployment, user acceptance or external rollback.

Git and Codex have complementary roles

Use Codex to explain a diff, identify a missing regression case or draft a recovery plan. Verify the baseline in Git. When rejecting a change, preserve unrelated work through a targeted correction rather than requesting unrestricted repository cleanup.

Reference answer & rubric Try the exercise before opening

Identify exactly what the index or commit protects and never call a clean-looking report complete acceptance.

When it does not work

Git asks for identity while following the optional lesson.

Likely cause: A normal commit was attempted instead of the supplied index-only workflow.

What to try: Use the provided index exercise or a file copy; leave personal identity unchanged.

The candidate diff includes unrelated files.

Likely cause: Staging or editing scope was too broad.

What to try: Review the named files and preserve work outside the exercise before proceeding.

Common mistakes

  • Using git add . in a shared working tree without inspecting every included file.
  • Treating a commit, passing test or saved transcript as a universal record of all project and external state.
