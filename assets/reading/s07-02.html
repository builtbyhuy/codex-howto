Understand the approach

Plugin architecture should start with a user journey: what information enters, which operation is needed, what result is returned, and how it is checked. The package is a delivery unit, not an architecture by itself. For a README review plugin, a skill may read a user-selected document and produce evidence-linked suggestions without a server. For live records, an MCP server supplies the controlled service boundary.

Keep responsibilities explicit. Skills define the method, expected output, decision points, and fallback behavior. MCP tools expose actual operations and enforce service-side authentication and authorization. Optional UI can help users inspect structured results, but is not necessary for a text-only workflow. Hooks attach to documented lifecycle points and require reviewed definitions plus runnable scripts in the execution environment.

The source architecture bundles commands, agents, MCP, hooks, and configuration. Codex plugin architecture provides related building blocks, but a source component does not automatically map one-to-one. Turn reusable command or agent procedures into an appropriate supported skill when needed. Treat local hook execution and cloud-orchestrated Work as different paths. Installing a package on the web does not deploy its local executable scripts.

Design the unhappy path first

For a document review, specify what happens when the document is missing, its instructions conflict with the user's request, or its examples contain private credentials. A useful result identifies the missing or suspicious material without executing it. If a later server is disconnected, the plugin should explain the gap instead of replacing live facts with invented data. These behaviors belong in the architecture because they shape the user's experience, not just developer diagnostics.

An installed copy can differ from the source

The marketplace points to authoring files, while native installation may use a cached copy. Inspect the returned installed path/version; changing the source alone does not prove an existing session is using it. The extension task changes the server and manifest to 0.3.0 so this distinction is observable.

  1. Start with the skill's instruction to discover the tools and list fixture IDs. It provides the method but does not itself supply external permissions.
  2. Trace the local client through initialize and initialized, tools/list, then review_fixture_readme with a known ID. The server reads only the fixed packaged fixture.

When it does not work

A tools/call made immediately after process launch fails.

Likely cause: MCP initialization and the initialized notification were skipped.

What to try: Follow the lifecycle in client.cjs and wait for discovery before requesting a review.

The skill invents findings after a tool error.

Likely cause: Workflow recovery did not preserve the failed state.

What to try: Use the skill's error branch: name the failed operation and missing evidence, then stop or retry the bounded call.

Common mistakes

  • Putting access-control rules only in a skill while the service accepts unrestricted operations.
  • Treating optional UI, hooks, agents, and a server as mandatory plugin boilerplate.
Source mapping & differences · different

The modular architecture purpose transfers, but Codex's skills/MCP/optional UI/hooks boundaries and surface compatibility replace source-specific command and agent bundles.
