Understand the approach

A plugin packages reusable capabilities so people can discover and install them. In ChatGPT and Codex, it can combine skills, MCP-backed tools, and other supported components. A skill supplies reusable workflow instructions; an MCP connection supplies operations and data. Packaging them together can reduce repeated setup, but does not automatically grant access to a service or permission for every action.

The source introduces plugins as a bundle of Claude commands, agents, hooks, and configuration. Preserve that reuse goal while checking each Codex component independently. Current documentation supports plugins in the desktop app and Codex CLI, with one universal public directory shared across supported ChatGPT surfaces. The IDE extension explicitly does not support plugins. Standalone IDE skills or MCP connections are separate capabilities, not evidence of IDE plugin support.

Choose packaging when a workflow must be installed or shared as a coherent unit. For a single repository convention, AGENTS.md or a local skill may be enough. Installation, enablement, connection authentication, hook trust, and successful use are distinct states. A plugin can be installed while its server is disconnected, its hooks await review, or a requested record is inaccessible. Report the actual state instead of treating an install receipt as proof of a working integration.

Use the least packaging that helps

A skills-only package is a useful first example because its inputs and outputs can remain local and inspectable. If later users need live ticket data, add a connection only after defining records, fields, and allowed actions. If a visual interface would improve a real task, evaluate it separately. Starting small makes setup failures easier to isolate and keeps the package's promise aligned with what it can actually deliver.

Reference answer & rubric Try the exercise before opening

Choose packaging only when the reusable capability and its installation audience justify it; prove its smallest operation first.

  1. Run the complete and missing-checks cases. Explain the concrete difference in their outputs rather than describing a hypothetical tool.
  2. Identify the skill as the review method, the local tool as deterministic fixture access, and hooks as optional feedback. None grants access to external records.
  3. For one project convention, compare a saved prompt, a repository skill, and this multi-component plugin. Recommend the least setup needed for the actual audience.
  4. Use the package when the same skill and tool should travel together. Keep desktop/CLI support distinct from the IDE extension, which does not support plugins.
  5. The isolated native metadata lifecycle was tested. Use NATIVE-CLIENT.md for your own version/discovery/install/removal observations, then prove authenticated skill/tool use and hook delivery separately when supported.

When it does not work

The complete fixture receives a missing-verification finding.

Likely cause: The wrong fixture was selected, or the checker was modified incorrectly.

What to try: Inspect the named file and rerun both cases. Preserve the zero-findings control case before changing packaging.

Someone expects installing the package to authorize every action.

Likely cause: Packaging, technical connection, and task authorization were conflated.

What to try: Describe the fixed fixture scope and require a separate request before edits, accounts, sending, or external access.

Common mistakes

  • Assuming a plugin automatically gives access to all connected-service data.
  • Adding an MCP server or hook just to make a small instructions-only package seem more complete.
