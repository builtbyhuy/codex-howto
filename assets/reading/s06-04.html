Understand the approach

An event name tells you when a hook runs, which inputs it receives, and how its result is interpreted. PreToolUse runs before supported tool operations; PostToolUse sees their output after execution. SessionStart can supply context, while Stop can request continued work at the end of a turn. Selecting an event because its name sounds suitable is insufficient: timing determines what the hook can still influence.

Codex documents twelve lifecycle events across session start/end, subagent start/stop, prompt submission, tools, permission requests, compaction, stopping, and interruption. Do not import the source course's larger event matrix as a Codex promise. Matchers also have event-specific meaning. A SessionStart matcher filters the start source; PreToolUse filters tool names; Stop and UserPromptSubmit currently ignore matcher settings.

PostToolUse cannot undo a completed side effect. For Bash it also runs after a non-zero command exit, so seeing the event does not mean the command succeeded. PermissionRequest only runs when an approval would be requested; it is not a check on every ordinary operation. Stop's blocking decision asks Codex to continue, which differs from denying a pending tool. Record these distinctions in the event map.

Compare prevention with later information

The deny-move fixture inventories a protected destination before any patch executes. Separately, workflow-plugin/hooks/demo.cjs replays SessionStart, successful PostToolUse, and failed PostToolUse input. The informational handler supports both those event kinds; other events return an empty object. Its PostToolUse message cannot undo an operation. Optional actual-client observations should record event, source or tool name, output, and effect on the supported host rather than claiming coverage of every tool.

One event, one interpretation

The same handler output cannot be reused blindly across events. Stop continuation creates another agent turn; it does not roll back a patch or certify correctness. The classroom Stop checker ends the retry when stop_hook_active is true, leaving the user a specific unresolved state instead of an endless loop.

Think it through

Check your understanding

A PostToolUse hook reports that a completed command changed a file. What can it guarantee?

  1. It can automatically rewind every changed file.
  2. It proves the command exited successfully.
  3. It can provide documented feedback, but cannot undo the side effect.
Reveal the answer and explanation

Answer 3: It can provide documented feedback, but cannot undo the side effect.

The event is after execution, and Bash PostToolUse can include unsuccessful commands. Recovery requires a separate, authorized action.

When it does not work

A protected rename is allowed by a naive check.

Likely cause: Only the original Update File path was inspected.

What to try: Inventory Move to destinations and mixed patch operations before returning no objection.

The after-tool warning is mistaken for prevention.

Likely cause: The event occurs after execution.

What to try: Review the resulting state and propose any recovery separately; do not claim rollback from a feedback message.

Common mistakes

  • Using PostToolUse as though it could reverse an external write.
  • Adding a matcher to an event that ignores it, then assuming the hook is narrowly scoped.
