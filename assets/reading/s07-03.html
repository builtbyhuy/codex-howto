Understand the approach

New portable plugins use plugin.json at the package root. Skills live under the root skills/ directory; portable MCP configuration, when needed, uses root mcp.json with its transport declarations. A simple skills-only plugin can begin with identity fields and one SKILL.md. You do not need to scaffold unused servers, hooks, assets, or credentials. Keep the plugin's stable kebab-case name separate from a friendly display label.

Codex also supports a compatibility layout using .codex-plugin/plugin.json. The current creator can still scaffold that supported format with .mcp.json and optional resources. Do not rename the files mechanically and assume portability: the portable MCP format has its own schema and transport type. For a new manual package, follow the current portable guide; for an existing compatibility package, understand its actual manifest before changing it.

OpenAI-specific metadata belongs in extensions.com.openai in the portable root manifest. If that object is present, it replaces the compatibility overlay's OpenAI-specific settings rather than merging with it. Referenced resource paths must start with ./, resolve from the plugin root, and remain inside the package. Credentials do not belong in any manifest. A structurally valid file still needs workflow tests and source/license review.

Names, paths, and ownership are different checks

A stable name helps hosts identify the package; safe paths keep resources inside its boundary; a license explains permitted reuse. Passing one check does not imply the others. If adapting third-party material, retain its required notices and identify your modifications. Do not copy the source course's author identity into your own package as though you were that publisher. Use truthful metadata when a real release is prepared.

A concrete versioned change

The complete extension reference changes identity metadata only where needed: stable package name remains, version advances from 0.2.0 to 0.3.0, server metadata follows it, and the separate output schema accepts the added bounded fixture. The grader catches mismatches instead of accepting a version string in a release note.

Keep a root portable manifest, a schema-correct stdio entry, a focused skill, and package-contained references.

  1. Inspect root plugin.json and identify its stable name, version, description, and extensions.com.openai local-executor and hook fields.
  2. Inspect mcp.json: type stdio, command node, the ${PLUGIN_ROOT}/server.cjs argument, and plugin-root cwd. Confirm the actual file exists.

Does a new portable skills-only manifest need a skills field?

  3. Only if its filename starts with a dot.
Reveal the answer and explanation

Answer 1: No; portable skills are discovered from the root skills/ directory.

The current portable format uses fixed package locations. Compatibility manifests can use different declarations, so identify the format first.

When it does not work

The manifest parses, but the server is not found after moving the folder.

Likely cause: A machine-specific or catalog-relative path replaced the plugin-root placeholder.

What to try: Use ${PLUGIN_ROOT} in the portable stdio entry and revalidate the actual scratch package.

A compatibility package loses interface or hook settings after migration.

Likely cause: The portable OpenAI extension replaces the compatibility overlay instead of merging it.

What to try: Move the required OpenAI-specific settings deliberately and check the final effective package; do not rename manifests mechanically.

Common mistakes

  • Mixing portable and compatibility manifest assumptions without checking which settings take precedence.
  • Copying a source .claude-plugin manifest or putting API keys into package metadata.
