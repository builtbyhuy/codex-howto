Understand the approach

AGENTS.md is a plain Markdown file for instructions that should outlive one conversation. The CLI /init command generates a starting scaffold in the current directory. In the desktop app or IDE, you can also ask Codex to draft project guidance from the files it inspects. This is a writing task with consequences: an inaccurate instruction can be repeated in every later task, so the generated draft needs review.

Begin with facts visible in the scratch repository. Identify the project purpose, the documented run and test commands, and the files that should not be modified routinely. If a command is absent, record the gap instead of adopting a familiar npm script. Add a small working agreement about checking results and preserving unrelated changes. A short accurate file is more useful than a long generic engineering policy.

Inspect any existing AGENTS.md before generating or replacing it. There may already be important local rules or another contributor’s changes. In this lesson, create guidance only inside the disposable practice project and leave your Codex home untouched. Once the file is reviewed, start a fresh session in that project and ask which instruction sources loaded. Discovery happens at session startup, so a stale session is a poor test of a newly written file.

Initialize from repository evidence

The starter already has useful instructions, so blindly running initialization risks replacing them. Draft into AGENTS.proposed.md first. Verify each path and command: checks.cjs exists, package.json does not, and WORK-NOTE.md must survive. Keep the original object-preservation contract.

After review, integrate into AGENTS.md and start a fresh session at the intended project. Ask for loaded source paths and the test command. In the optional CLI track /init generates a scaffold inside the current directory. It is a composer control, not a terminal command or proof that the scaffold’s assertions are true.

Review guidance like code

Read each sentence as a future instruction. Replace vague demands with observable expectations and verify commands against the repository. Keep task authority separate from build documentation. Improve the smallest relevant guidance file instead of duplicating policies globally.

Try it step by step

  3. Use CLI /init, or ask for a project-local draft, then edit the result to remove unsupported claims and broad permissions.

When it does not work

The scaffold includes an absent package script.

Likely cause: The initializer inferred a familiar toolchain.

What to try: Replace it with the verified command or explicitly record the gap.

Changes do not affect the running session.

Likely cause: Instruction discovery may have occurred before the edit.

What to try: Test a fresh session in the intended directory instead of assuming a cache failure.

Common mistakes

  • Running initialization from a parent workspace and unintentionally setting rules for unrelated projects.
  • Keeping scaffold suggestions such as npm test when the project has no corresponding script.
