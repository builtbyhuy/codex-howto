Understand the approach

Permission controls answer different questions: where commands may act, when an operation needs review, and who reviews eligible requests. The sandbox defines technical file and network boundaries; approval policy determines when Codex asks; the selected reviewer can route eligible requests to a person or automatic review. These layers should be explained separately instead of reduced to a single safe or unsafe label.

The source lists Claude-specific mode names. Codex app and IDE use their current permission controls, while CLI documents /permissions and flags such as --sandbox and --ask-for-approval. Available choices and managed constraints can vary. A configuration field shown in documentation is not proof that it is active in this chat. Inspect effective settings and writable locations before diagnosing a blocked action.

Task authorization remains another boundary. A request to inspect code does not authorize modifying production, even if technical access is broad. Conversely, already-authorized routine work inside a suitable boundary should not require repeated unnecessary confirmation. Choose the smallest access that meets the actual task. If a check fails, identify the precise operation and missing capability rather than turning off restrictions globally.

Document the exception, not a permanent broadening

If an authorized task genuinely needs another directory, identify that directory and the minimum action before choosing a supported scoped mechanism. Record whether the exception is once, for a session, or persistent. A future task may not need it. Keep the validation evidence with the project so a later operator knows why access was required and does not mistake an old exception for a standing instruction to use every available resource.

  2. Perform a small project-local edit in a generated project and inspect actual file/tool evidence under that selected environment.
  3. For the deliberate OS boundary test launch a separate read-only CLI with never approval. Request a tiny scratch file and inspect actual denial or startup failure plus file absence.
  4. Compare the result with workspace-write/on-request. Explain why never removes prompting and does not grant permission, and why a model refusal alone is not enforcement evidence.
  5. End the probe and restore the app’s original mode. Keep technical boundaries distinct from the hook’s narrower lexical path policy.

When it does not work

A read-only request is assumed safe merely because the sandbox permits a write.

Likely cause: Technical capability was confused with task authorization.

What to try: Keep the requested scope read-only; propose a change for review instead of using every available permission.

A sample permission file differs from the observed behavior.

Likely cause: Managed policy, platform, or the current session can affect effective settings.

What to try: Use the actual permission control and runtime error as evidence, then consult the relevant platform and managed-configuration documentation.

Common mistakes

  • Equating approval_policy never with read-only or treating no prompt as approval of the task.
  • Changing global permissions to solve a path or runtime error that did not require broader access.
