Understand the approach

Scheduled tasks start stable work at a chosen cadence. In the desktop app, open Scheduled, choose the project, prompt, cadence and execution environment, then save the task you intend to run. A Git project can use its local directory or an isolated worktree; a non-Git project uses the local directory. The CLI and IDE can prepare the workflow but do not provide the Scheduled management interface.

Test the prompt in a regular app chat first. For local project tasks keep the computer on, app running and folder available. A standalone task starts independent runs; scheduling inside an existing chat preserves its context. Web tasks can use accessible uploads and connections but cannot directly operate on a PC folder. Model availability, organization policy and unattended permissions can affect a run.

A task creation receipt is not a successful run. Inspect the first actual output under Scheduled, verify its scope and evidence, then edit the prompt or cadence if needed. Pause the practice task and verify its status/next-run change; remove it through the task controls when finished. The course itself does not create a schedule on your account, but the learner track teaches the complete workflow rather than only preparing a proposal.

Try it step by step

  1. Open the generated package as an app project and run the prompt manually; verify a missing heading produces real evidence.
  2. Open Scheduled and create a task. Choose that project, the prompt, displayed cadence/timezone, and local or Git-worktree execution deliberately.
  3. Review the displayed configuration and next run, then save when you intend it to run. Record the actual task state rather than a draft JSON proposal.
  4. Inspect the first actual run (or the build’s manual run action when offered). Check output, tool activity, missing context and unattended failures.
  5. Edit the task if required, pause it and confirm its status/next-run change, then remove the practice task and confirm it is no longer active.

When it does not work

The displayed next run is not the local time you intended.

Likely cause: The selected cadence/timezone differs from your intended schedule, including daylight-saving behavior.

What to try: Edit the actual task’s schedule controls, inspect its next run and verify the resulting timezone before leaving it active.

A quiet run is treated as proof that the schedule worked.

Likely cause: No-change, failure, and not-run states were combined.

What to try: Inspect last execution, failure/complete state and actual result separately. Suppress only successful no-change results according to the task prompt; pause and repair a failing schedule.

Common mistakes

  • Assuming a local scheduled task runs while the computer or app is off.
  • Treating a missing task as permission to create a replacement without schedule-specific approval.
