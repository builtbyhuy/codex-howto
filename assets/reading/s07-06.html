Understand the approach

Choose a distribution channel for the intended audience: repository marketplace, admin-managed workspace publication, or public directory submission. These have different ownership, eligibility and consumer steps. This lab supplies a complete local marketplace and versioned package; the release guide shows the actual Git ref, consumer installation, update and removal flow rather than ending at a readiness record.

For a repository marketplace, test the exact package, commit the catalog and package, tag the tested revision, and publish through your normal repository process. Consumers add the Git source with --ref, inspect the marketplace and installed version, and test a new chat. A local tag or JSON validation is not distribution. A pinned source remains pinned when refreshed; rollback explicitly selects a known-good ref and repeats verification.

Workspace admins can publish a local plugin to chosen roles from the Personal plugin menu. Public publication instead uses the Plugins portal: upload an eligible ZIP, resolve findings, submit for review, then publish the approved version. The current portal rejects lifecycle hooks/app references, so this hook-bearing local lab cannot be submitted unchanged. No account publication was performed by the course author; the lesson still teaches the executable publisher and consumer path.

Prepare the right review evidence

For an MCP-backed submission, the current guide asks for five positive cases, three negative cases, a walkthrough, release notes, and a dedicated reviewer account when sign-in is required. Do not fabricate executed cases or create credentials for this lesson. A skills-only package can have a different requirement set. Mark every missing artifact and recheck the current portal guidance before requesting approval for a real submission.

Reveal the answer and explanation

Answer 1: No; the publisher chooses when to publish the approved version.

The documented flow separates review approval from the explicit publication step. A license field does not change that state.

When it does not work

The package passes schemas, so the release is labeled publicly eligible.

Likely cause: Structural validity was confused with submission requirements.

What to try: Inspect current component eligibility and retain explicit hooks/local-stdio blockers in the readiness record.

An uploaded draft is announced as published.

Likely cause: Upload, review approval, and public publication were collapsed into one state.

What to try: Report the actual portal state and destination; perform each external transition only after the required authorization.

Common mistakes

  • Claiming a local package or successful upload is publicly approved.
  • Submitting hook-dependent or app-reference packages without checking current public-directory restrictions.
