Understand the approach

A scripted task can produce several kinds of output. In ordinary codex exec mode, progress goes to stderr while the final agent message goes to stdout. That distinction helps when a shell saves a report. The --output-last-message option, also available as -o, saves the final answer to a named file. Choose a new report path rather than redirecting into a source file you meant only to inspect.

With --json, stdout becomes a stream of JSON Lines events: each line is a separate JSON object describing progress or an item. This is not one large JSON document and not necessarily just the final answer. A consumer must parse each line and distinguish completion from failure. Saving a final message alongside an event stream gives you both an inspectable summary and execution evidence without confusing their formats.

For a stable machine-readable final result, --output-schema requests a response shaped by a JSON Schema. The schema constrains structure, not factual truth. A project name can satisfy a string field while still being invented. Include a way to report unknown information, compare returned values with the actual project files, and validate the saved output with the downstream tool that will consume it.

Structure can pass while the facts fail

The wrong answer has every required field and allowed type, but invents npm test and a deployment URL while omitting deployment_url from unknowns. The validator reports structure: valid and facts: rejected. A malformed object or missing field fails the structural gate; a missing source format is unverifiable.

This checker is intentionally limited to the fixture’s explicit Project, Check and Deployment lines. It is not a universal README or JSON Schema engine. JSONL belongs in report.cjs, where each line and lifecycle transition is checked. A complete stream and producer exit zero cannot turn a fabricated URL into a fact.

A report file is evidence of output, not success

A saved output can still contain gaps. Inspect its source and decide whether the task passed. If a parser consumes the file, test an unknown value and a failed run first. This exercise creates local reports; it does not configure CI or schedules.

When it does not work

JSON.parse rejects the entire capture.

Likely cause: JSONL is several JSON values separated by newlines, not one JSON document.

What to try: Parse nonblank lines separately and preserve line-numbered failures.

A printed final message is accepted after truncation.

Likely cause: The consumer never required the last turn to complete.

What to try: Keep the message pending until completion and reject an incomplete last turn.

Common mistakes

  • Passing an entire JSONL stream to a parser that expects one JSON object.
  • Assuming schema compliance proves the extracted project facts are correct.
