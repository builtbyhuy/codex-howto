Understand the approach

A directory is where users discover plugins; a marketplace source is a catalog that tells a supported client which packages are available. ChatGPT and Codex share a universal public directory, while local or team catalogs can provide other packages. A listing is not the same as installation, enablement, connected-service authentication, or authorization for the task you want the plugin to perform.

The desktop app provides plugin browsing and installation. In Codex CLI, /plugins opens the plugin browser, and documented marketplace commands can inspect or register sources. The IDE extension does not provide plugin support. A repository catalog can live at .agents/plugins/marketplace.json, with entries pointing to package folders. source.path resolves relative to the marketplace root, not the catalog's nested .agents/plugins directory.

The lab now generates a complete active catalog in a new scratch root and provides a child-only native client helper. It runs the real marketplace commands with a disposable CODEX_HOME; it does not copy login data or edit the owner’s configuration. Inspect source ownership, contents, version, license and data destinations before using any remote source. Managed requirements may still restrict availability in ordinary clients.

Choose a reproducible source

For a real team rollout, record the package version and the source reference you reviewed. A moving branch can change after approval, and a display name alone is not a stable identifier. Keep the reviewed contents available for comparison with later updates. If policy blocks a source, treat that as a constraint to resolve with the owner rather than a reason to mirror or reinstall it through an unreviewed channel.

A useful starting example

Illustration · adapt before use.

Guarded workspace setup and native version check · PowerShell powershell
$pluginPracticeRoot = & {
  $ErrorActionPreference = 'Stop'
  $createdRoot = & node labs/workflow-plugin/create-workspace.cjs --path-only
  if ($LASTEXITCODE -ne 0 -or @($createdRoot).Count -ne 1 -or [string]::IsNullOrWhiteSpace($createdRoot)) { throw 'Plugin workspace creation failed; no native action was run.' }
  $resolvedRoot = (Resolve-Path -LiteralPath $createdRoot).Path
  if ((Split-Path $resolvedRoot -Leaf) -notlike 'codex-howto-workflow-*' -or -not (Test-Path -LiteralPath (Join-Path $resolvedRoot 'PRACTICE-WORKSPACE.json') -PathType Leaf)) { throw 'Expected generated workspace is missing.' }
  $resolvedRoot
}
node labs/workflow-plugin/native-client.cjs version $pluginPracticeRoot
if ($LASTEXITCODE -ne 0) { throw 'Native version check failed; stop here.' }

From where does a local source.path resolve?

  1. Always the .agents/plugins folder.
  2. The user's current browser download directory.
  3. The marketplace root.
Reveal the answer and explanation

Answer 3: The marketplace root.

The documented root determines path resolution. Confusing it with the catalog folder can make an entry point to the wrong or missing package.

When it does not work

The same catalog works at one root but finds no plugin when relocated.

Likely cause: source.path was resolved from the catalog file's directory instead of the marketplace root.

What to try: Write down the chosen marketplace root, resolve the relative path there, and validate the target manifest again.

A similarly named remote listing is treated as official.

Likely cause: Name similarity was used as provenance.

What to try: Inspect the actual owner, source revision, package contents, and license; do not register the source until its provenance is understood.

Common mistakes

  • Copying the source's Anthropic marketplace commands into a Codex workflow.
  • Treating a public listing, trusted-looking name, or installed state as proof of appropriate access and behavior.
Source mapping & differences · different

Codex uses its universal directory and documented local/Git marketplace catalogs, not the source's Anthropic marketplace names or commands.
