Understand the approach

A hook attaches a small operation to a point in Codex's lifecycle. Instead of asking the agent to remember a check in every prompt, you define when a script or an existing MCP tool should run. Useful examples include adding short repository context at session start or inspecting a pending tool operation. The trigger, handler, and interpretation of its result form one contract; a script alone is not a working hook.

The source course introduces several Claude hook mechanisms. Codex provides the same broad event-driven capability, but its supported handlers, events, and response fields differ. Current documentation supports command and mcp_tool handlers. Hooks from multiple active sources can match the same event, and matching command hooks can start concurrently. Do not rely on one hook running before another or preventing another handler from starting.

Start with the fictional fixture suite, then connect the same handler in a disposable project. The generated native track writes a complete project-local configuration with the actual host interpreter path. It lets you observe discovery, definition trust, a covered allowed edit, a protected edit denial, and disabling. These are separate from a program merely printing correct JSON. Keep personal configuration out of this first experiment.

Observe the policy before trusting it

The lab begins with an offline policy precisely so its outcomes can be observed without preventing a real operation. Compare a no-objection response, explicit denial, irrelevant tool, handled-invalid input, and a process that never launched. A production credential filter would need a stronger threat model and broader coverage. Keep this small guard's lexical path and tool limits visible; completing its classroom exercise does not make it universal protection.

What this first hook actually establishes

The guard inventories paths in canonical apply_patch input before the operation. It is a deliberately small lexical rule, not a filesystem sandbox: other tools and symlinks remain outside its coverage. Native success means the particular covered tool event was observed and handled in that client, not that every possible file write is prevented.

Reference answer & rubric Try the exercise before opening

A successful overview lab distinguishes the policy's decisions from its integration and coverage limits.

  1. Match allow.json to a permitted in-root path and deny-protected.json to a protected destination.
  2. Identify irrelevant.json as a tool outside this apply_patch-only policy; do not call it universally permitted or universally protected.
  3. Explain why malformed stdin returns a denial response after the handler starts, while a missing executable cannot return a policy decision.
  4. Retain the no-live-client label and state symlink, shell-write, and other-tool coverage gaps.
  5. For the extension, change the separate learner.cjs candidate, not the frozen guard. Preserve every baseline non-allow result, then deny a normalized root-level generated/ path while allowing src/generated-helper.js. Pass the same candidate regression gate used by the reference.
  6. For native practice, follow NATIVE-CLIENT.md through discovery, current-definition trust, covered tool observation and disabling; record unrun stages honestly.
Think it through

Check your understanding

What makes a hook operationally meaningful?

  1. A script with a memorable filename.
  2. Any instruction that says always.
  3. A supported event, a runnable handler, and a tested result contract.
Reveal the answer and explanation

Answer 3: A supported event, a runnable handler, and a tested result contract.

A hook is an event-to-handler integration. Naming a script or repeating an instruction does not establish when it runs or how Codex interprets its result.

When it does not work

Every fixture seems blocked.

Likely cause: The fixture uses a malformed canonical apply_patch payload or an ambiguous root.

What to try: Start with allow.json and compare hook_event_name, tool_name, cwd, and tool_input.command before changing policy.

The local tests pass but no hook appears in Codex.

Likely cause: Offline tests exercise a Node program, not client discovery or trust.

What to try: Use the separate optional scratch-client procedure and record discovery, trust, delivery, and effect independently.

Solving the extension appears to require breaking a baseline assertion.

Likely cause: The learner changed the frozen guard instead of the separate editable candidate.

What to try: Restore guard.cjs and test.cjs, implement the extension in learner.cjs, and run both the candidate gate and the unchanged suite.

Common mistakes

  • Treating a reminder in AGENTS.md as proof that an executable check always runs.
  • Assuming all matching hooks run in a dependable sequence or that installation automatically trusts them.
